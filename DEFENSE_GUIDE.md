## 1. АРХИТЕКТУРА И ФУНДАМЕНТ (Общий план)

Приложение построено на **Laravel 11** (PHP 8.2+). Это современный MVC-фреймворк.

### 1.1. Что такое MVC в вашем проекте?
*   **Model (Модель):** Файлы в `app/Models`. Они "знают" всё о данных в БД (User, Post, Message).
*   **View (Вид):** Файлы в `resources/views`. Это в
аши Blade-шаблоны, то, что видит пользователь.
*   **Controller (Контроллер):** Файлы в `app/Http/Controllers`. Это "дирижер", который принимает запрос от пользователя, просит данные у Модели и отдает их Виду.

### 1.2. Структура ядра (app/Http/Kernel.php)
Этот файл — "входные ворота" для всех HTTP-запросов.
*   **`$middleware`**: Глобальные фильтры (например, проверка на режим техобслуживания).
*   **`$middlewareGroups['web']`**: Набор фильтров для обычных страниц (куки, сессии, защита от CSRF).
*   **`$middlewareAliases`**: Псевдонимы для фильтров. Например, `auth` — это стандартный фильтр проверки входа, а `admin` — ваш кастомный фильтр прав доступа.

## 2. МАРШРУТИЗАЦИЯ И ДОСТУП (routes/web.php)

Маршруты определяют логику URL-адресов. В проекте используется группировка для чистоты кода.

### 2.1. Middleware 'auth'
```php
Route::middleware('auth')->group(function () { ... });
```
Эта группа защищает весь основной функционал. Если пользователь не вошел в систему, Laravel (через посредника `Authenticate.php`) перенаправит его на страницу логина.

### 2.2. Кастомный Middleware 'admin' (app/Http/Middleware/EnsureAdmin.php)
**Разбор кода:**
```php
public function handle(Request $request, Closure $next): Response {
    if ($request->user()->role !== 'admin') {
        abort(403); // Если роль не админ — выкидываем ошибку доступа
    }
    return $next($request); // Иначе — пропускаем запрос дальше
}
```
**На защите скажите:** "Я реализовал ролевую модель доступа. Middleware `admin` гарантирует, что обычный сотрудник не сможет попасть в панель управления или удалить чужой пост".

## 3. МОДЕЛИ И БАЗА ДАННЫХ (Eloquent ORM)

Вместо SQL мы используем объекты. Разберем ключевые модели.

### 3.1. Модель User.php (Пользователь)
*   **`$fillable`**: Защита от "массового заполнения". Мы разрешаем менять только те поля, которые указали (имя, email, телефон). Поле `role` намеренно отсутствует в `$fillable` в некоторых местах, чтобы его нельзя было подменить через обычный запрос профиля.
*   **`$hidden`**: Список полей, которые не будут видны, если превратить объект в текст (JSON). Мы прячем пароль.
*   **Связь `groups()`**: 
    ```php
    return $this->belongsToMany(GroupChat::class, 'group_members')
                ->withPivot('role');
    ```
    Это связь **Многие-ко-многим**. Мы говорим: "Один юзер может быть во многих чатах, а в одном чате много юзеров. Информацию о том, кто там кто, бери из таблицы-посредника `group_members`".

### 3.2. Модель Post.php (Пост)
*   **Связь `comments()`**: `hasMany(Comment::class)`. Laravel сам поймет, что нужно искать в таблице `comments` поле `post_id`.
*   **Связь `positiveLikes()`**: Это фильтрованная связь. Она возвращает только те лайки, где поле `like` равно `true`.

## 4. КОНТРОЛЛЕРЫ (Разбор логики "по шагам")

### 4.1. PostController.php (Метод index — Главная лента)
```php
$posts = Post::query()
    ->with(['user', 'attachments', 'comments.user'])
    ->withCount(['positiveLikes as likes_count', 'comments'])
    ->latest()
    ->get();
```
*   **`with(...)` (Eager Loading)**: Это самая важная строчка для производительности. Если её убрать, сервер будет делать 101 запрос в БД для 100 постов (проблема N+1). С ней — всего 3-4 быстрых запроса.
*   **`withCount(...)`**: Laravel сам считает количество лайков и комментов прямо в SQL-запросе, не загружая сами объекты лайков. Это очень быстро.

### 4.2. MessageController.php (Метод storeDirectMessage — Личка)
Этот метод — пример сложной логики.
1.  **`$request->validate(...)`**: Проверка входящих данных. Ограничение файла в 5МБ (`max:5120`).
2.  **`Message::query()->create(...)`**: Сохранение сообщения в таблицу `messages`.
3.  **`$this->storeDirectAttachments(...)`**: Если есть файлы, они проходят через `FileUploadService`.
4.  **`event(new ChatMessageBroadcast(...))`**: Самый важный момент. Мы создаем событие, которое через долю секунды доставит сообщение в браузер получателя без обновления страницы.

## 5. ТЕХНОЛОГИЯ AJAX (Как работает "живой" интерфейс)

**AJAX** (Asynchronous JavaScript and XML) — это когда JavaScript отправляет запрос серверу в фоновом режиме.

### Пример: Лайк под постом
1.  **На фронтенде (JS):** Вы нажимаете на кнопку. Скрипт вызывает функцию `fetch()`.
2.  **На бэкенде (PHP):** Метод `PostController@toggleLike` получает запрос.
    *   Он проверяет: "Стоял ли лайк?".
    *   Если да — `delete()`, если нет — `create()`.
    *   Возвращает **JSON**: `{ "liked": true, "likes_count": 5 }`.
3.  **Снова на фронтенде (JS):** Получив этот JSON, скрипт находит на странице цифру лайков и меняет её на 5, а иконку — на закрашенную. **Перезагрузки всей страницы нет!**

## 6. ВЕБ-СОКЕТЫ (LARAVEL REVERB) — Погружение с нуля

Это технология, позволяющая серверу самому писать клиенту (Push-уведомления).

### 6.1. Зачем это нужно?
В обычном HTTP вы не узнаете, что вам написали, пока не обновите страницу. С Веб-сокетами сервер Reverb держит соединение открытым и мгновенно "проталкивает" новые данные.

### 6.2. Как это реализовано в коде?
1.  **Broadcasting Event (app/Events/ChatMessageBroadcast.php):**
    *   Класс имеет интерфейс `ShouldBroadcastNow`. Это значит: "Отправляй мгновенно, не жди очереди задач".
    *   **`broadcastOn()`**: Метод возвращает `PrivateChannel('users.' . $id)`. Это гарантирует безопасность: только пользователь с этим ID может "слушать" этот канал. Проверка прав идет в `routes/channels.php`.
    *   **`broadcastWith()`**: Здесь мы выбираем, какие именно данные (текст, аватарку) отправить.
2.  **Broadcasting Channel (routes/channels.php):**
    ```php
    Broadcast::channel('users.{id}', function ($user, $id) {
        return (int) $user->id === (int) $id; // Можно слушать канал только если ID в ссылке совпадает с твоим ID
    });
    ```
3.  **Клиентская часть (resources/js/echo.js):**
    Мы используем **Laravel Echo**. Она подключается к серверу Reverb (настроен в `.env`).
    Когда Echo слышит событие `chat.message` в канале пользователя, она запускает функцию, которая добавляет новое сообщение в чат.

## 7. СЕРВИСЫ: FileUploadService.php

Это паттерн "Service". Вместо того чтобы писать код загрузки файлов в каждом контроллере, мы вынесли его в отдельный класс.
*   **`store()`**: Проверяет тип файла (картинка или документ), создает папку, генерирует уникальное имя (`Str::uuid()`) и перемещает файл в `public/uploads`.
*   **Почему UUID?** Чтобы хакеры не могли угадать имена файлов или заменить один файл другим с таким же именем.
*   **`remove()`**: Безопасно удаляет старые файлы с диска, когда пользователь меняет аватар или удаляет пост.

## 8. БЕЗОПАСНОСТЬ (Ваши козыри на защите)

1.  **CSRF (Cross-Site Request Forgery):** В каждом AJAX-запросе (`X-CSRF-TOKEN`) и каждой форме есть скрытый ключ. Это доказывает, что запрос пришел именно с вашего сайта, а не от злоумышленника.
2.  **XSS (Cross-Site Scripting):** Благодаря Blade-синтаксису `{{ $text }}`, любой вредоносный скрипт в посте превратится в безобидный текст.
3.  **SQL-инъекции:** Laravel использует PDO (Prepared Statements). Данные от пользователя никогда не попадают в SQL-запрос напрямую.
4.  **Хеширование паролей:** Мы используем **Bcrypt** через фасад `Hash::make()`. Пароли хранятся в виде нечитаемого кода, который невозможно расшифровать обратно.

## 9. ЧАСТЫЕ ВОПРОСЫ КОМИССИИ И ОТВЕТЫ

*   **В: Почему Laravel 11?**
    *   **О:** Это самая современная версия с поддержкой Reverb "из коробки" и упрощенной конфигурацией.
*   **В: Как вы храните файлы?**
    *   **О:** Файлы хранятся на сервере в папке `public/uploads`, а пути к ним — в базе данных. Это стандартный и эффективный подход.
*   **В: Зачем нужны миграции?**
    *   **О:** Это система контроля версий для базы данных. Они позволяют развернуть проект на любом компьютере одной командой `php artisan migrate`, гарантируя идентичность структуры таблиц.
*   **В: Что такое ORM Eloquent?**
    *   **О:** Это способ работы с базой данных на языке объектов PHP. Она делает код более читаемым, безопасным и позволяет легко менять СУБД (например, с MySQL на PostgreSQL) без переписывания всего кода.
